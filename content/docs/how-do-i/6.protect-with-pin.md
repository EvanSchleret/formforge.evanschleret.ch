---
title: Protect a form with a shared code
description: Require a shared code before showing a form or before accepting a submission.
---

FormForge supports two independent shared codes. Use a submission code to protect response submission, or use an access code to require a challenge before the API returns the schema.

## Protect only response submission

The management API accepts these fields and stores only the server-side hash of the code:

- `submission_code_required`
- `submission_code`

The renderer shows the submission-code input after it loads the schema and includes the value in the submission metadata.

## Protect schema access

Set `access_code` and `access_code_required` through the management API or `FormForgeSettings`. The renderer first checks the access status endpoint and starts a challenge without loading the schema. After the visitor verifies the code, the renderer keeps the temporary authorization in memory and sends it in `X-FormForge-Access-Token` for schema and public form operations.

The API stores only a server-side hash. Challenge and authorization lifetimes, failed attempts, route throttling, and cache storage are configurable in the backend. See [Access-code challenge](/docs/backend/http-api/schema-submission-upload-resolve#access-code-challenge) for the HTTP contract and configuration.

This shared code does not verify a visitor's identity and must not be described as MFA. It does not grant access to management routes.

## Good practice

- Use access-code protection when the schema itself must stay private until a visitor enters the shared code.
- Use submission-code protection when visitors may view the form but must enter a code to submit.
- Keep API enforcement enabled; hiding a client-side control alone does not protect the form.

::warning
Do not treat a client-side control as a security boundary. The backend must enforce both challenge authorization and submission-code requirements on their respective endpoints.
::
