## Access-code challenge

Access-code protection is separate from `submission_code`, which continues to protect response submission. The public status endpoint only reports whether a challenge is required; it does not return a schema, fields, or access-code metadata.

1. Discover whether the form requires a code:

```http
GET /api/formforge/v1/forms/customer-survey/access
```

```json
{ "data": { "required": true } }
```

2. Start a short-lived challenge. The response contains only an opaque challenge identifier and its expiry:

```http
POST /api/formforge/v1/forms/customer-survey/access-challenges
Content-Type: application/json

{}
```

```json
{
  "data": {
    "challenge_id": "opaque-random-id",
    "expires_at": "2026-10-25T18:05:00+00:00"
  }
}
```

3. Verify the code in the request body. A successful verification consumes the challenge and returns a temporary bearer capability:

```http
POST /api/formforge/v1/forms/customer-survey/access-challenges/opaque-random-id/verify
Content-Type: application/json

{ "code": "visitor-shared-code" }
```

```json
{
  "data": {
    "access_token": "opaque-temporary-token",
    "expires_at": "2026-10-25T18:15:00+00:00"
  }
}
```

Keep the authorization in memory and send it in `X-FormForge-Access-Token` when loading schema revisions or calling the public resolve, field-validation, upload, and submission endpoints. The token is intentionally reusable across those required operations until it expires. It cannot call management or draft endpoints and is bound to the exact form, route scope, and resolved owner. A code change invalidates outstanding authorizations.

The API does not reveal a protected schema before verification. Missing authorization returns `401` with `access_required`; an expired or mismatched authorization returns `403` with `access_invalid`. Incorrect codes return `422` with `invalid_code` and `attempts_remaining`. The last failed attempt returns `429` with `attempts_exceeded`; route throttling also returns `429`. Expired challenges return `410` with `challenge_expired`, and a challenge from another form or scope returns `404`. A consumed challenge cannot be used again. Starting a challenge for a form without an access code returns `404` with `not_found`.

Challenge lifetime, authorization lifetime, and failed-attempt limit are configurable with `formforge.access_challenge.challenge_ttl_seconds`, `authorization_ttl_seconds`, and `max_attempts`. Challenge routes use `formforge.http.access.middleware`, which defaults to `throttle:30,1`. The cache store is `formforge.access_challenge.cache_store` and defaults to Laravel's configured cache store; multi-node applications should use a shared cache backend. The challenge identifier is an opaque locator, not an authorization. Do not put the code or returned token in a URL, logs, analytics, or persistent browser storage.

For cross-origin browser integrations, allow the `X-FormForge-Access-Token` request header in the host application's CORS configuration. Normal endpoint authentication and authorization rules still apply in addition to this access capability.

The status, challenge, and verification routes must be enabled in each route scope that uses protected forms. The schema and other public endpoints remain independently configurable for that scope.

## Submission

- `POST /forms/{key}/submit`
- `POST /forms/{key}/versions/{version}/submit`

Payload input keys are accepted by canonical field `name` and by `field_key` (default mode: `both`).

Examples:

```json
{
  "payload": {
    "name": "Evan",
    "email": "evan@example.com"
  }
}
```

```json
{
  "payload": {
    "fk_abc123name": "Evan",
    "fk_def456mail": "evan@example.com"
  }
}
```

If both `name` and `field_key` are sent for the same field, `name` wins.

## Resolve

- `POST /forms/{key}/resolve`
- `POST /forms/{key}/versions/{version}/resolve`
- `POST /forms/{key}/validate-field`
- `POST /forms/{key}/versions/{version}/validate-field`

`validate-field` checks a single field value in isolation. Unlike `submit`, it does not validate or persist a full form payload.

Request body:

```json
{
  "field": "email",
  "value": "john@example.com"
}
```

Success response:

```json
{
  "valid": true,
  "errors": [],
  "validated": {
    "email": "john@example.com"
  }
}
```

Failure response:

```json
{
  "valid": false,
  "errors": [
    "The email field is required."
  ],
  "validated": []
}
```

If `field` is missing from the request body, validation fails with a 422 response from the request validator.
